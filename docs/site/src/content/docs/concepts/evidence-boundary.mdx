The session is the evidence, and a model may only propose. What gets written, loaded or executed is decided by record types and counters, not by a prompt.

## Two sides

| | In the session | Outside the session (detached binary runs) |
|---|---|---|
| Runs | the omp extension (or a harness adapter) | the Rust binary |
| Does | records every input, tool result and turn; flags; loads; runs approved hooks | classifies, proposes, lints, stages, counts, decides |
| Model calls | none | editor and classifier, through `omp -p` |
| Parses | nothing: it forwards raw events | everything: the schema lives in Rust only |

No proposal exists without a trace ([D1](/rematch/background/decisions/)). The binary never holds provider credentials; every model event's provider and model are verified.

## What a proposal can and cannot do

- **It carries no score, validation or approval field.** Scoring, retention (`accepted_in_use`, `comparative_support`, `user_decision`, `legacy`), probe outcomes and approvals belong to the engine and ledger, never to editor JSON ([D24, D31](/rematch/background/decisions/)).
- **Nothing activates without a lint report.** Anything executable, always-on in your personal `AGENTS.md`, or replayed as a probe also needs a receipt or task authorization ([D24, D29, D31, D32](/rematch/background/decisions/)).
- **Skill, rule and fact text activate on their own,** in your personal scope, as a place-scoped provisional trial (`trials` in `status` and `library ls`).
- **Personal instructions, scripts, hooks, subagents and probe replays wait in the persistent action queue.** Scripts are staged mode 0644; hooks are compiled only after approval ([D4](/rematch/background/decisions/)); a provisional subagent is linked nowhere and an `AGENTS.fragment.md` reaches no prompt until you approve the exact snapshot you inspected.
- **Anything beyond your machine waits for an explicit branch or export** (`ship-team:<id>`, `fork:<id>`, `export:<id>`).

<Aside type="note" title="Why executable changes wait">
Compiled hooks raised compliance with user corrections from 55.0% to 70.1% in the Trace paper. They are also the form that can act without being read.
</Aside>

## Lint is the generalization gate

Every staged entry passes static lint ([D15](/rematch/background/decisions/)):

- no session ids, task paths or user names in the text;
- no string-match on the user's words;
- a trigger predicate and a trigger line on every entry;
- no URLs, network calls or destructive git;
- catalog metadata and on-demand body budgeted separately ([D30](/rematch/background/decisions/)): each `description` ≤ 1,024 B of plain single-line text (`catalog_text`), the session's always-on catalog ≤ 8,192 B (`always_on_bytes`: raw `name` + `description` lines of kept/pinned/profile entries and overlapping provisional entries/agents, plus applied personal instructions and fragments), and the on-demand `SKILL.md` router body ≤ 8,192 B (`router_bytes`);
- facts carry `as_of`.

The always-on budget is checked again when you approve an instruction or subagent, because pending approvals can each fit alone and overflow together. HarnessCompass's generalization gate alone recovered most of its gain. Full rule set: [lint rules](/rematch/reference/lint/).

## Scope and who merges

Every approval below binds the snapshot you inspected: `library approve|decline <id> --sha <hash>`, with the hash supplied by `/rematch review` or by the command `library inspect <id>` prints ([the review flow](/rematch/guides/approve-scripts-and-hooks/#the-review-flow)).

| Scope / action | Activation | Examples |
|---|---|---|
| Personal, trial text (`trials`) | automatic, as place-scoped `provisional` | skill text, laws, facts, lessons (`description` ≤ 1 KB, router body ≤ 8 KB) |
| Personal instructions (`instructions:<id>`) | approve the action; declining keeps the entry | a marked `<!-- rematch:begin name=<name> ... -->` block in your personal `<agent_dir>/AGENTS.md` (omp reads the file) and matched-session runtime insertion in Claude Code, Pi and OpenCode; never `<repo>/AGENTS.md` ([D29, D32](/rematch/background/decisions/)) |
| Applied instructions (`instructions-applied:<name>`) | decline withdraws; profile-wide when the profile carries the text | blocks in effect now, or approved but over the budget |
| Edited block (`instructions-conflict:<name>`) | approve restores rematch's text (or removes the block); decline keeps your edit as your own | you edited inside a rematch block; `off`, `disable` and `uninstall` never overwrite or delete an edited block |
| Personal, executable or subagent (`<entry-id>`) | approve the action; declining retires the entry | scripts (`0644 → 0755`), compiled hooks (`rematch-hooks/<id>.ts`), provisional subagents (`AGENT.md`, scoped per place) |
| Bounded automatic probe (`probe:<id>`) | approve the exact task; declining skips auto-probes for that repo and keeps the entry on the observed-use path | one baseline and one candidate omp rollout (≤ 300 s each, 1 per pass, 4 per 24 h) in detached `HEAD` worktrees with sealed editable paths ([automatic probes](/rematch/guides/automatic-probes/)) |
| Team (`ship-team:<id>`, `<repo>/.omp/`, `<repo>/AGENTS.md`) | approve the action, or run `ship --scope team`: builds a local branch from `HEAD`; `--push --pr` opens the PR, never merges | entries whose predicate recurred across ≥ 2 repos, or that you list; the only way text reaches a repo's `AGENTS.md` |
| Fork (`fork:<id>`) | approve the action, or run `ship --scope fork`: builds a local branch in the fork checkout | per-model prompt text, tool descriptions, compaction defaults |
| Work → home (`export:<id>`) | approve the action per entry, or `library export --entry <id> --approve` after reading its diff; off by default at work | invariant entries only; lint with `transfer: true` blocks domain and workspace facts |

## Branches and `shared`

- A **branch** is a repo or project. Entries are staged per branch.
- **`shared`** holds entries kept in two or more branches. Promotion needs a second branch's canary and no new canary of its own.
- When the shared copy replaces a kept entry whose task has a verifier, that task is replayed once first. A failing replay retires the copy; the kept entry stays.
- **Transfers** between branches with overlapping facets are applied as provisional and earn their place through that branch's counters.
