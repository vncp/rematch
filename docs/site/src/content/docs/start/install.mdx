Install the binary, connect your harness, and check the connection.

One binary, ledger and library serve every harness; an adapter only forwards what its harness exposes. omp is the reference. What each harness can and cannot do: [harness capabilities](/rematch/reference/harnesses/).

## Install

<Tabs syncKey="harness">
<TabItem label="omp">

You need omp 18.12 and a Rust toolchain, in a checkout of this repo.

<Steps>

1. Build and link:

   ```sh
   scripts/install.sh
   ```

   It builds the binary, links the extension into omp, and writes the shim `~/.local/bin/rematch`.

2. Check:

   ```sh
   rematch doctor --text
   ```

   The last line reads `ready: true`. Anything else is listed as a `problem:` line saying what to run.

</Steps>

<Aside type="note" title="What install.sh does">
- `cargo build --release` (`--locked` when `Cargo.lock` exists).
- Links `extension/agents` → `~/.rematch/agents` (for subagent entries).
- `omp plugin link extension --scope user`.
- Writes `~/.local/bin/rematch`, which runs `target/release/rematch` of the checkout.
- Runs `rematch doctor` and prints the optional model roles.
</Aside>

<Aside type="note" title="Windows">
Turn on Developer Mode (Settings → System → For developers): every library view is a symlink, and Windows lets a normal user create one only there. `rematch doctor` reports it as a `problem:` otherwise. Then run, in PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install.ps1
```

It does what `install.sh` does; the shim is `~\.local\bin\rematch.exe`, a symlink to `target\release\rematch.exe`, and that directory is added to your user `PATH`. `scripts\uninstall.ps1` undoes it.
</Aside>

</TabItem>
<TabItem label="Claude Code">

You need Claude Code 2.1.285 or later and the `rematch` binary: `cargo build --release` in this repo, `rematch` on `PATH`, or `REMATCH_BIN` set.

<Steps>

1. Load the plugin in every session:

   ```sh
   ln -s /path/to/rematch/adapters/claude-code ~/.claude/skills/rematch
   ```

   Or for one session only:

   ```sh
   claude --plugin-dir /path/to/rematch/adapters/claude-code
   ```

2. Check the load:

   ```sh
   claude --plugin-dir /path/to/rematch/adapters/claude-code plugin details rematch
   ```

   Expect 8 hooks; under Skills, the nine commands plus every kept skill; under Agents, the kept rematch subagents.

</Steps>

<Aside type="caution" title="Use one of the two routes above">
A marketplace install copies the plugin and drops its `skills/` link. `~/.claude/plugins/` is Claude Code's marketplace cache.
</Aside>

Reflection makes its model calls through omp (`OMP_BIN`, else `omp` on `PATH`). Without omp, sessions are still traced, flagged and loaded; run `rematch reflect --pending` where omp is installed.

If large sessions end unflagged, raise the 1.5 s `SessionEnd` budget:

```sh
CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS=5000 claude
```

</TabItem>
<TabItem label="Pi">

Use Pi 1.4.x (`@earendil-works/pi-coding-agent`) and Node 22.19 or newer. Keep this checkout available: the adapter imports Rematch's shared helpers from it.

<Steps>

1. Build Rematch and put its binary on your shell's path:

   ```sh
   cargo build --release
   export PATH="$PWD/target/release:$PATH"
   ```

2. Install the local Pi package:

   ```sh
   pi install "$PWD/adapters/pi"
   ```

   For one session instead:

   ```sh
   pi -e "$PWD/adapters/pi"
   ```

3. Start Pi and check:

   ```text
   /rematch status
   ```

</Steps>

Pi discovers the session place's skill view (`~/.rematch/views/<key>/skills`) through its native resource-discovery hook. Tracing and approved runtime hooks run in Pi; background reflection still needs omp with configured model access.

<Aside type="note" title="Which Pi?">
This adapter targets the maintained `@earendil-works/pi-coding-agent` package. The older `@mariozechner/pi-coding-agent` package is not the tested target.
</Aside>

Remove the package with `pi remove /path/to/rematch/adapters/pi`. See the [adapter notes](https://github.com/vncp/rematch/blob/main/adapters/pi/README.md) for session resume behavior and limits.

</TabItem>
<TabItem label="OpenCode">

Use OpenCode **1.19.4** and a local Rematch checkout. OpenCode 2 is not a tested target.

<Steps>

1. Build the Rematch binary:

   ```sh
   cargo build --release
   export PATH="$PWD/target/release:$PATH"
   ```

2. Add this entry to the existing `plugin` array in your global
   `~/.config/opencode/opencode.json`, or a project's `opencode.json`:

   ```json
   {
     "plugin": ["/path/to/rematch/adapters/opencode"]
   }
   ```

   Merge it with your existing configuration; do not replace other plugins.

3. Start OpenCode and check:

   ```text
   /rematch-status
   ```

</Steps>

The plugin adds the session place's skill view (`~/.rematch/views/<key>/skills`) to OpenCode's in-memory skill paths.
It traces main sessions, runs approved hooks, and provides user commands for approvals.
Reflection still needs omp with configured model access.

<Aside type="note" title="Finishing a session">
OpenCode's idle event ends a turn, not the session. Rematch waits for process disposal,
crash recovery or its documented quiet-session cutoff before finalizing evidence.
A later continuation gets a new trace segment rather than rewriting counted history.
</Aside>

See the [OpenCode adapter](https://github.com/vncp/rematch/blob/main/adapters/opencode/README.md)
for supported hooks, session boundaries and history import.

</TabItem>
<TabItem label="Codex">

You need `rematch` on `PATH` (`scripts/install.sh`, or `cargo build --release`). The omp plugin is not required. Nothing runs inside a Codex session; rematch reads its sessions afterwards.

<Steps>

1. Let Codex see rematch's skills (once):

   ```sh
   mkdir -p ~/.agents/skills
   ln -s ~/.rematch/skills ~/.agents/skills/rematch
   ```

2. Before starting Codex in a git repo, sync the skills and repo-scoped trials that match it:

   ```sh
   rematch skills sync --harness codex --cwd "$PWD"
   ```

   Kept skills load through `~/.agents/skills/rematch`; the repo's provisional trials load through a git-excluded link `<repo>/.agents/skills/rematch-trials`.
   To do it on every launch, add this to your shell rc:

   ```sh
   codex() { rematch skills sync --harness codex --cwd "$PWD" >/dev/null; command codex "$@"; }
   ```

3. After you worked, import and reflect:

   ```sh
   rematch import --history --harness codex
   rematch reflect --history
   ```

   A session that was never imported never counts.

4. Optional: digest, sync and approvals from inside Codex, each command after your approval:

   ```sh
   ln -s "$PWD/adapters/codex/skills/rematch-status" ~/.agents/skills/rematch-status
   ```

</Steps>

</TabItem>

## Choose the models (optional)

The editor should be the strongest model you have, the classifier a fast one. Set them in `~/.omp/agent/config.yml`:

```yaml
modelRoles:
  rematch-editor: <provider>/<strongest model>      # falls back to slow → default
  rematch-classifier: <provider>/<fast model>       # falls back to smol → tiny → default
```

`rematch doctor --text` shows which models it resolved. Per-machine roles: [model roles](/rematch/reference/configuration/model-roles/).

## Seed from your history (optional)

Import the sessions you already have, then reflect on the ones that carried a correction. Import is read-only and makes no model call.

```sh
rematch import --history
rematch reflect --history
```

- `import --history` reads available omp, Claude Code, Codex, Pi and OpenCode history. Use `--harness omp|claude-code|codex|pi|opencode` to select one, or `--skip-profile <name>` to exclude an omp profile. Each adapter documents its history location and environment overrides.
- `reflect --history` handles the newest 10 flagged sessions per run (`--limit`, `--since 2026-10-01`). Run it again for the next batch; a session is reflected once.
- Each reflection follows the same rules as a live one: same rate limits, at most 3 model calls.
