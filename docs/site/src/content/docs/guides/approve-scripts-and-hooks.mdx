Skill, rule and fact text, **data-only hooks** (`block`, `stuck`, `truncate`, `retrieve`, `check`), and **read-only subagents** activate automatically as scoped provisional trials and appear under `applied_automatically` with a one-command undo (`rematch library rollback <name>` or `rematch library disable <id>`; `rematch off` withdraws all).

Pending review (`actions`) holds what still needs a person: personal `AGENTS.md` instructions, write-capable subagents, and scripts (unless covered by a standing `policy auto` rule), plus unsealed probe replays, exports, and team or fork branches ([D29, D32](/rematch/background/decisions/)).

<Aside type="caution" title="Nothing waits out of sight, and nothing automatic is hidden">
Every automatic adoption is listed in `applied_automatically` of `rematch status`, `rematch digest` and `rematch library ls` with what it is, where it lives, why it applied (`data-only`, `read-only`, `rule`, `comparative_support`, or `probe_regressed`), and its undo command. Every item that still needs a person stays in `actions` until you approve or decline it.
</Aside>

## The review flow

1. **See what waits.** omp and Pi show `◆ rematch ● N needs you: … alt+e review` above the editor; Claude Code and OpenCode list the waiting actions at session start (and in Claude Code's optional `scripts/statusline.sh` footer); `rematch status --text` lists them anywhere.
2. **Inspect.** `library inspect <id>` shows the whole proposal: what it writes or runs, where (target and per-host reach), its scope, the reason, the full diff, and the exact approve and decline commands.
3. **Approve or decline.** Both commands carry `--sha <hash>`: the 64-hex hash of the snapshot you just reviewed (`review_sha256`). The review dialog and the listed commands supply it, so you never copy it by hand in omp or Pi.

The hash covers the action's id, entry and version, content hash, target, scope, reach, state, reason, summary and the exact diff. If any of them changed since you looked, rematch refuses the decision and asks you to inspect again. A missing or shortened hash is refused too.

## What waits in the action queue

Each item has a typed `id` that you pass to `library inspect`, `library approve` and `library decline`:

| Action ID | What approving does | What declining does |
|---|---|---|
| `<entry-id>` (kind `scripts`, `agent`, joined with `+`) | makes `scripts/*` mode `0755` (after reviewing the script and its sandbox dry-run observations); links the write-capable provisional subagent into `~/.rematch/agents/` (Claude Code: a copy in matching repos' `.claude/agents/`) | **retires** the entry |
| `instructions:<entry-id>` | writes the fragment as a marked block into your personal `<agent_dir>/AGENTS.md` (omp) and turns on runtime insertion in Claude Code, Pi and OpenCode | declines that text only; **the entry stays** |
| `instructions-conflict:<name>` | **restores** rematch's block over your edit (or removes it, if no text is approved any more) | **releases** the block: the markers go and your edited text stays as your own |
| `instructions-sync` | rewrites the personal `AGENTS.md` to what your approvals and on/off say (after a failed write or a fixed permission) | — |
| `probe:<entry-id>` | authorizes bounded automatic replay of that exact task ([automatic probes](/rematch/guides/automatic-probes/)) | no replay in that repo; its entries stay on the observed-use path |
| `ship-team:<entry-id>` | builds a local branch `rematch/<name>-…` for the team repo in a temporary worktree; never pushes | stops the offer until the entry changes |
| `fork:<entry-id>` | builds a local branch in your omp fork checkout; never pushes | stops the offer until the entry changes |
| `export:<entry-id>` | writes the invariant entry to `~/.rematch/export/` (work → home) | stops the offer until its content changes |

Two more kinds are listed but cannot be approved:

| Action ID | What it is | Declining |
|---|---|---|
| `instructions-applied:<name>` | a personal instruction block in effect now (state `applied`), or an approved one that does not fit the budget (state `blocked`) | **withdraws** it (see [withdrawing](#withdraw-an-applied-block)) |
| `fragment-unreadable:<entry-id>` | an approved fragment Claude Code, Pi and OpenCode cannot read, so they skip it | withdraws that runtime approval; the entry and any `AGENTS.md` block stay |

A `blocked` action names why it cannot be approved and the command that fixes it; it has a decline but no approve command. In `digest`, `status` and `library ls`, diffs are cut at 4,096 bytes; `library inspect` shows them whole.

The model's own `rematch` tool, and shell commands it runs, are refused for every user-only control (approve, decline, pin, unpin, disable, rollback, export approval, mark, on, off, uninstall, `policy scope set|unset`, `policy auto`, `policy probes` mutations), wherever the global flags sit. That is a control-plane rule, not a sandbox.

## Standing `policy auto` rules and sandbox dry runs

- **Data-only hooks (`block`, `stuck`, `truncate`, `retrieve`, `check`) and built-ins** compile on stage and run immediately as scoped provisional trials. If a `block` hook fires and is followed in the same session by a user correction/preference redirect or a `disable`, that session counts as **harm** (`RETIRE_AT = 2` retires it); if the agent completes the task cleanly without the blocked action, it counts as a clean use.
- **Read-only subagents** whose `AGENT.md` `tools:` frontmatter is a subset of `read`, `grep`, `glob`, `find`, `lsp*`, `web_search`, `fetch`, `web_fetch` are exposed in matching places without approval. Subagents that omit `tools:` or request write/shell tools wait in `actions`.
- **Scripts** run once on stage inside an OS sandbox dry run (`sandbox-exec` on macOS, `bwrap` on Linux) that denies network access and writes outside a temporary scratch directory. The dry run never approves a script by itself; its observed behavior (clean exit, temp writes, or blocked outside writes / network access) is recorded and included on the `scripts` review item in `actions`.
- **Standing rules (`rematch policy auto add|remove|list <surface> <scope>`, user-only)** let you opt in to automatic approval for `scripts`, `agents` or `instructions` in a repo path, normalized remote, or `**` (instructions still respect `limits.always_on_bytes`), recording `"rule:<surface>:<scope>"` as the approver in the receipt.
## Personal `AGENTS.md` instructions

An entry can carry an `AGENTS.fragment.md`: short text that belongs in the system prompt. Its personal home is your own user-level `AGENTS.md`, never a repo's.

### Where the text goes

| Host | How it gets the approved text |
|---|---|
| omp | from the file: a marked block in `<agent_dir>/AGENTS.md` (`~/.omp/agent/AGENTS.md` in the default omp profile), which omp loads in every session. Nothing is injected at runtime, so the text never arrives twice. |
| Claude Code | runtime insertion: session-start context of main sessions where the entry matches |
| Pi | runtime insertion: appended to the system prompt of matched main sessions |
| OpenCode | runtime insertion: the system transform of matched main sessions |
| Codex | not supported; skills only |

The runtime hosts record `fragments_sent` with the approved hash of each block they actually sent (Claude Code only when the context fits its 10,000-character cap); omp records the blocks its file held (`instructions_exposed`). Either counts as use of the entry.

The block looks like this:

```markdown
<!-- rematch:begin name=<name> sha256=<inner-sha> fragment=<fragment-sha> pad=<n> -->
## rematch: <name>

<approved fragment text>
<!-- rematch:end name=<name> -->
```

### Lifecycle

- **Approve.** `instructions:<entry-id>` shows the exact block diff, the target file and each reach. Approving writes the block and turns on runtime insertion. An approval from the earlier runtime-only flow does not cover the file: rematch asks again and marks that reach as new.
- **Your text is preserved.** Bytes outside the markers are never touched, and a symlinked `AGENTS.md` is written through and stays a link. If rematch created the file, removing its last block deletes the empty file; a file that was yours stays.
- **Changes ask again.** A revised fragment waits as a new `instructions:<entry-id>` while the approved text stays in place.
- **Decline.** Declining `instructions:<entry-id>` declines that text only; the skill keeps running.
- **Off, disable, retire, uninstall.** `off` removes unchanged blocks and `on` restores them; disabling or retiring the entry removes its block; `uninstall` removes every unchanged block. An edited block is never removed or rewritten.
- **New sessions only.** A running session keeps the text it was already sent.

### Edited blocks (`instructions-conflict:<name>`)

If you edit inside a block, its inner hash no longer matches and rematch stops managing it. Nothing overwrites it; `instructions-conflict:<name>` appears instead. Its diff shows both sides: the block as you left it and what rematch would write.

- **Approve** restores rematch's text over your edit (or removes the block when nothing is approved any more).
- **Decline** keeps your edit as your own text: the markers go, and the approved text is withdrawn so it is not added again.

If your edit or rematch's text changes after you inspected it, both are refused until you look again. A file that cannot be read, or whose marker lines do not parse, is left alone and shown as blocked until you fix it by hand.

### Withdraw an applied block

Blocks in effect are listed under `applied` in `status`, `digest` and `library ls`, with a line pointing at `rematch library inspect instructions-applied:<name>`. Declining that action withdraws the text: Claude Code, Pi and OpenCode stop receiving it first, then the block leaves your `AGENTS.md`. A withdrawn text is not offered again for the same bytes by itself.

<Aside type="caution" title="Withdrawal is profile-wide">
With a [profile](/rematch/concepts/profile/), approved texts travel to your other machines and omp profiles. Withdrawing a text that the profile carries, including one approved on another machine, withdraws it **everywhere**: the next `rematch profile sync` removes it from `profile/instructions/` and records the withdrawal, and every synced machine drops it at its own sync. The inspect output says so before you decide. A later approval of the same bytes brings it back.
</Aside>

### Budget

All blocks together must fit `limits.always_on_bytes` (8,192 B by default, `improver/lint.toml`). The check runs when you approve, next to everything else rematch keeps always on where the entry loads, and again whenever the file is synced, including texts arriving from the profile:

- An approval that would not fit shows as `blocked` with the numbers and asks you to withdraw another block or shorten the fragment.
- A text that arrives over the budget (from the profile, or after you lower the limit) is not written. It waits as a blocked `instructions-applied:<name>` action, and the blocks already in the file keep their place.

### When the file cannot be written

A failed write (a read-only file or directory) is recorded, never reported as a removal. `instructions-sync` stays in the queue with the error until a write succeeds; fix the permissions, then approve it.

### Team `AGENTS.md`

A repo's `AGENTS.md` is a separate, optional route. It is written only on a branch, when you approve `ship-team:<id>` or run [`rematch ship --scope team`](/rematch/guides/share/).

## Hook modes

| Mode | What it does |
|---|---|
| `block` | blocks a tool call whose input field matches a pattern, with the rule's message |
| `stuck` | blocks a call identical (same tool, same arguments) to the N calls right before it; any other call in between resets it |
| `truncate` | in the request sent to the model (never in the session file), tool outputs older than N user turns keep their first K characters, ending `…[rematch: truncated N chars, age K turns]` |
| `retrieve` | before each request, appends one hidden message with the units of your loaded skills that match what you just asked and the files just touched, within a byte budget |
| `check` | after file-editing tool calls, runs the repo's detected fast check (`rematch check`: Cargo, tsc, ruff, pyright, mypy, Go) scoped to the edited files plus `git grep` references for changed signatures in unedited files, and injects one compact message (≤ 4,096 B) before the next turn |

## Built-in hooks

Four data-only hook entries ship with rematch. They live in branch `shared`, match every session, and run automatically as trials (disable any with `rematch library disable <id>`):

| Entry | Mode | Setting |
|---|---|---|
| `context-unit-retrieval` | `retrieve` | ≤ 6000 bytes, units sharing ≥ 2 stems with the request |
| `tool-output-truncation` | `truncate` | outputs older than 6 user turns keep 1200 characters |
| `stuck-detector` | `stuck` | the 4th identical call in a row is blocked |
| `fast-check` | `check` | ≤ 30 s timeout, ≤ 4096 bytes of compiler/linter diagnostics, unedited caller impact, or `✓ <check> clean` after file edits |

They are ordinary entries under the same counters:

- They compile on stage and run automatically as provisional trials (listed in `applied_automatically`).
- A session counts as use when the hook evaluates or applies (`hook_evaluated`, `hook_applied`, `check_ran` with fixed errors).
- Kept (`accepted_in_use`) after four clean completed sessions of such use.
- Retired after two sessions with a recurring correction or preference, or two with harm (error cluster, takeover, post-block redirect, or disable).

```sh
rematch builtins ls                   # status of the four built-ins
rematch builtins reinstall [name]     # stage a retired one again
```
