By default, a provisional entry earns `kept` either through sustained clean use in your normal sessions (`accepted_in_use`) or through a **bounded automatic probe** that compares the baseline library against the candidate in omp (`comparative_support`, [D31](/rematch/background/decisions/)).

Probes run **automatically, without a `probe:` approval**, whenever the task replays a recorded session of that repo in an isolated worktree, the verifier is engine-chosen and sealed (the repo's detected fast check `check`, detected test suite `tests`, or an observed plain test-runner command), and the run fits the budget (`probes.daily_runs`, default 3/day). The `probe:<entry-id>` review item appears only when a probe would use a user-supplied task/verifier or exceed rollout caps.

## How a probe works

In detached `reflect --pending` after a session ends (never while an active session is running, and never when rematch is `off`), rematch checks provisional entries for probe eligibility:

<Steps>

1. **Ground the task and sealed verifier (`suggest_for`).**
   For an eligible provisional entry, rematch grounds a replay in the originating trace: task id `probe-<name>-<short entry id>-v<version>`, the prompt before the correction, the last plain test-runner command observed in the session (else the repo's detected fast check `check`, then detected `tests`) as the verifier, and the files the session changed (minus protected ones) as `--editable`, with tools `read,grep,glob,edit,write`. A session that wrote no files gets a read-only task (`--tools read,grep,glob`, nothing editable).

2. **Run automatically when engine-chosen and within budget (or surface `probe:<entry-id>` for user-verifier tasks).**
   When the task is trace-grounded, its verifier is engine-chosen and sealed, and the run fits `policy.json` `probes` (`daily_runs`, default 3; `max_parallel`, default 1; per-rollout time cap ≤ 300 s), rematch runs the probe automatically without waiting for approval.

   If the probe uses a user-supplied task/verifier (`rematch task add`) or exceeds caps, rematch adds a one-tap hash-bound `probe:<entry-id>` action to the persistent action queue (`status`, `digest`, `library ls`):

   ```sh
   rematch library inspect probe:<entry-id> --text
   rematch library approve probe:<entry-id> --sha <hash>   # as printed by inspect
   ```

   Declining (`rematch library decline probe:<entry-id> --sha <hash>`) records the repository in `~/.rematch/probes/declined-repos.json`; its entries stay on the observed-use path.

3. **Run two isolated rollouts in detached `reflect --pending`.**
   Rematch runs the task twice through omp in fresh detached `HEAD` git worktrees:
   - **baseline:** your `kept` and `pinned` library for that repo (no other provisional trials);
   - **candidate:** the same baseline plus the provisional entry.

   Task, prompt, fixed verifier, tools, solver model, first seed and base `HEAD` commit are held identical.

4. **Check the seal, attribute and apply the verdict immediately.**
   After both rollouts finish, rematch checks that the repo's `HEAD` did not move, that neither rollout modified any path outside the task's declared `editable` scope or any protected verifier/test file, and that the candidate rollout actually read the entry. Verdicts apply immediately (`supports` → keep as `comparative_support`; `regresses` → retire; `tie`/`incomplete` → fall back to `accepted_in_use`) and appear in the next digest under **applied automatically** with an undo command (`rematch library rollback <name>` or `rematch library disable <id>`).

</Steps>

## Eligibility and sealed workspaces

Only entries that the omp rollout substrate actually mounts and reads are probe-eligible:

| Surface / condition | Probe eligibility | Why |
|---|---|---|
| `skill`, `rule`, `fact` with `.md` files only | **eligible** | mounted in the rollout's isolated skill directory and read on demand |
| entry with `scripts/`, `AGENTS.fragment.md`, `hook.json` or `kind: agent` | **skipped** (observed-use path) | rollouts run with `--no-extensions --no-rules`, memory off, and do not test host-specific or executable surfaces |
| mutating task with `--editable <repo-rel-path>…` | **eligible** | only listed non-protected paths (plus `parity:`/`receipt:` output files) may change; every other tracked or untracked non-ignored path is sealed |
| read-only review/analysis task with `--tools read,grep,glob` and no `--editable` | **eligible** | every repo path is sealed; any workspace write voids the comparison |
| empty `--editable` with writable or default tools | **blocked** | the judge cannot be sealed; add `--editable <path>` or `--tools read,grep,glob` |
| dirty git worktree or no `HEAD` | **skipped** | a detached `HEAD` worktree would not match the working tree |

Even when listed in `--editable`, verifier inputs stay sealed (`Task::is_protected`): files named in the verifier command, `test/`/`tests/`/`spec/`/`__tests__/`/`scripts/` directories, `*_test.*`, `test_*`, `*.test.*`, `*.spec.*`, `*.sh`, and build/test configs (`Cargo.toml`, `Cargo.lock`, `package.json`, `pyproject.toml`, `pytest.ini`, `Makefile`, `build.rs`, `go.mod`, etc.).

<Aside type="caution" title="A git worktree is not an OS sandbox">
Each rollout runs in a fresh detached `HEAD` worktree so your active checkout is untouched, and `git status --porcelain --untracked-files=all` checks tracked and new repo files afterwards. Git-ignored paths and anything outside the worktree are **not** checked or contained by an OS sandbox. Only authorize tasks and verifiers you trust to run in that repository.
</Aside>

## Outcomes and how they affect status

| Probe outcome | Meaning | Effect on the provisional entry |
|---|---|---|
| `supports` | candidate passed where baseline failed (or scored strictly higher), and the candidate rollout read the entry | **keeps** the entry as `comparative_support` if `recurrence == 0` and `harm == 0` |
| `regresses` | candidate failed where baseline passed (or scored strictly lower), and the candidate rollout read the entry | **retires** the entry |
| `tie` | same verdict and score (or the candidate never read the entry, so any difference is unattributable noise) | no decision; the entry continues on the observed-use path |
| `cost_worse` | tied verdict/score, but the candidate had more tool errors or > 1.5× the tokens | no decision; observational use still decides |
| `incomplete` | a rollout failed, timed out, drifted model, moved `HEAD`, or touched a sealed path | never promotes; the entry continues on the observed-use path |

## Budget and hard caps

| Cap | Value |
|---|---|
| Execution harness | omp only (`rematch-solver` → `default`) |
| When probes run | Detached in the background after a session ends (`reflect --pending`); never during an active session; stopped when rematch is `off` |
| Rollouts per probe | 2 (1 baseline, 1 candidate) |
| Host `--max-time` per rollout | ≤ 300 s (or the task's `--max-time` when lower), plus a 60 s engine outer deadline margin |
| Editor model calls | 0 (solver model calls happen only inside the two omp rollouts) |
| Concurrent probes (`probes.max_parallel`) | 1 (default; configurable in `policy.json`) |
| Daily budget (`probes.daily_runs`) | 3 per 24 hours (default; `rematch policy probes --daily N`, `0` = off) |
| Evaluations per `(entry, version, content_sha256)` | 1 |
| Concurrency locks | global `~/.rematch/probes/.lock` + per-task `~/.rematch/runs/<task>/.lock` |

Configure the daily probe budget or turn automatic probes off:

```sh
rematch policy probes --daily 3          # default: up to 3 automatic probes per 24h
rematch policy probes --daily 0          # turn automatic probes off
```

## Define or update a probe task by hand

If no test command was observed in the session, or a task is blocked because its editable scope is blank, define it explicitly:

```sh
# Mutating task: seal everything except src/lib.rs
rematch task add fix-parser --repo . \
  --prompt "Fix parser edge case for empty headers" \
  --verifier "cargo test" \
  --editable src/lib.rs

# Read-only review task: seal every repo path
rematch task add review-api --repo . \
  --prompt "Audit src/api.rs for panics and report line numbers" \
  --verifier "script:./check-report.py" \
  --tools read,grep,glob
```

Redefining a task changes its fingerprint and clears any prior `auto_probe` authorization, so the `probe:<entry-id>` action comes back for you to review and approve again.
