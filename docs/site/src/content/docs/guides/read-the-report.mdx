---
title: Read the report
description: Compute the kill criterion — did anything earn kept, and did recurrence fall — instead of eyeballing it.
---

`rematch report` answers the project's kill criterion from your history: has an entry been kept in real use (at least four clean completed sessions that actually used it), and has recurrence fallen on a trigger the library covers? Entries kept on comparative support are reported apart and never count as real use.

What the kill criterion is and why it exists: [counters and the kill criterion](/rematch/concepts/counters/#the-kill-criterion).

## Run it

```sh
rematch report --text                   # the last 6 weeks
rematch report --window 30d --text      # <n>w, <n>d or <n>h, ending now
rematch report --since 2026-09-15       # from that UTC day to now
```

It reads the lake when there is one (every machine's history after `lake import`), else this ledger's journal (`"source": "ledger"`). Without `--text` it prints the JSON envelope.

## Example output

From the seed of `report`'s unit test (one trigger, both arms, after `lake export`; machine name shortened):

```text

  trigger run-tests-before-commit [6675c0a0d803] class correction: with 0/4 recurred (0 redirect(s), rate 0.00) · before 2/4 recurred (2 redirect(s), rate 0.50) · Δ -0.50 fell
verdict: an entry kept in real use (≥ 4 clean actual uses): yes (run-tests-before-commit); recurrence fell on a covered trigger: yes (run-tests-before-commit); kept on comparative support: no
```

## Read it line by line

| Line | Says |
|---|---|
| `kept <name> [<retention>]` | an entry whose status at the window's end is kept, with why it was kept (`accepted_in_use`, `comparative_support`, `user_decision`, or `legacy` for keeps from before reasons were recorded) and, in the window: matched sessions (any machine), sessions that actually used it, how many of those were clean, how many had unknown completion, recurrence and harm |
| `domain <d>` | a summary of that domain's triggers; arms add up (a session matching two triggers counts twice) |
| `trigger <name> [hash]` | one trigger predicate: its two arms, `Δ`, and `fell` when `Δ` is negative |
| `verdict` | the two halves of the kill criterion, then the comparative keeps, with the names behind each `yes` |
| `profile-kept (not counted on this machine): N` | with a profile, skills kept on another machine (JSON `profile_kept`) |

In JSON, each `kept[]` item carries `matched`, `used`, `used_clean`, `use_unknown`, `recurrence`, `harm`, `retention`, `in_use` (`used_clean ≥ 4` with zero recurrence and harm in the window) and `comparative` (kept on comparative support). The `verdict` object is `{kept_in_use, kept_entries, recurrence_fell, fell_on, kept_comparative, comparative_entries}`.

- **Real use is clean actual use.** `in_use` needs four clean completed sessions that read, invoked, retrieved or otherwise used the entry. Matched sessions alone, however many, never satisfy it.
- **Unknown is not clean.** Sessions without native completion evidence (imported transcripts, old rows) are counted in `use_unknown` and never toward `in_use`.
- **Comparative support is separate.** A keep backed by a bounded probe shows under `comparative_entries`; it is evidence on one authorized task in omp, not a real-use gain.

## The two arms

Each session in the window that matches a trigger's files and terms, and whose domain fits, falls in one arm:

| Arm | The session |
|---|---|
| **with** | loaded an entry of that trigger |
| **before** | loaded none |

- Each arm shows sessions, sessions where the trigger's redirect class recurred, the redirects of that class, and the rate (recurred / sessions).
- `Δ` = with − before. A trigger is **covered** when its with-arm is not empty.
- A classless entry's redirect class is any correction or preference.
- Triggers are grouped by domain; `(none)` holds triggers without one.

## Rules that keep it honest

- Every row is read as the ledger held it at the window's end, so a past report does not change when entries move on.
- Built-in entries are listed but never count toward the verdict.
- After a predicate tune, each session is counted against the predicate of the version it loaded, so a wider predicate cannot win by matching more sessions.
